# 产品代码准入与薄 Harness 规则

> 文档状态：Current / Stable engineering contract
>
> 适用范围：产品设计、Agent Harness、Wails API、Sidecar、持久化、测试与交付评审
>
> 本文回答“什么代码可以进入并继续留在 MilkSU 产品链”。它不是实现队列，也不替代
> `current-objectives.md` 的当前优先级。

## 核心默认

新能力默认不进入产品。只有真实用户任务、已观察到的失败轨迹或不可推迟的安全边界，才能为
新增产品代码取得准入资格。

这里的“产品链”包括：

- release 构建及其生产依赖图；
- Wails 对外方法和 Vue 生产入口；
- Sidecar 包、默认 Agent 资源和启动路径；
- 持久化 schema、迁移与兼容逻辑；
- 用户可见设置、状态、入口和产品声明。

研究、fixture、benchmark 或 smoke 可以存在，但必须与产品链隔离。代码量不是判定标准；
没有当前产品责任、重复上游行为、不可达、默认关闭或只能证明自身存在，才是删除或隔离理由。

## 所有权边界

| 责任 | 默认所有者 | MilkSU 可以做什么 |
| --- | --- | --- |
| 模型 Session、上下文压缩、通用 Tool Loop、通用计划和子任务编排 | Pi 或经审阅的上游资源 | 固定版本、传递策略、投影事件和状态，不重写通用 Harness |
| 桌面授权、Workspace、Credential、路径、审批、外部效果和事件投影 | MilkSU | 实现并强制执行本地产品与安全边界 |
| Challenge、Evidence、Candidate、Judge Receipt、Recovery、Memory 和学习事实 | CTF Domain | 实现领域契约、独立判定与可追溯事实 |
| Smoke、fixture、benchmark、发布验收和回归报告 | 外部测试 Harness | 通过正常产品接口验收，不把测试控制器嵌入产品 |

设计新能力时，先判断上游是否已经拥有相同责任。若拥有，优先采用薄适配；若没有，但该能力也
不是 MilkSU 独有产品责任，则先保留为研究或隔离实验，不默认自建通用 Harness。

## 上游优先实现阶梯

通过设计准入不代表应立即自写实现。对已经准入的能力，按以下顺序选择机制，只有前一层有具体
不足时才进入下一层：

1. 直接使用操作系统、Git、Wails、Pi 或目标平台已经提供的当前能力；
2. 引入固定版本、可审阅的 Skill、MCP Server、插件、包或平台 CLI，并只写薄适配；
3. 在许可证兼容且来源可追溯时，提取上游最小代码片段；不能直接复用代码时，采用其已验证的
   协议或设计，并记录与上游的差异；
4. 最后才实现最小的 MilkSU 自有机制，并用真实失败轨迹与验收任务约束其范围。

“成熟”至少要求：源码可审阅、许可证兼容、仍在维护、权限与 Credential 范围可界定，并有与
当前任务相符的使用证据。下载量、Star 或模型推荐不能单独满足成熟性。引入上游依赖前仍须检查
版本固定、供应链、发布体积、离线行为、数据边界与退出成本；如果薄适配的总成本高于一个很小的
本地实现，可以选择后者，但必须记录判断，而不是悄悄重造同类框架。

MCP/Skill/插件还必须固定可见工具清单、描述与 schema；区分 read/write/execute/network/account
效果；限制工作区 root、环境变量与传输绑定；升级后重新审阅，不能把 Server 在线、菜单已选择或
模型自述调用成功当作领域完成。面向安全工具的资源先在普通 Coding 完成真实成功任务和越权拒绝，
再决定是否进入 CTF/CVE，且不能绕过 Challenge、Evidence、Finding 或 Judge 的领域事实链。

Coding Agent 任务默认采用一个结果导向的任务契约：目标、现有上下文、不可越过的边界和完成证据。
一个会话处理一个连贯结果；worktree、分支、依赖准备与恢复由会话基础设施承担。Reviewer 在开始
时给出一次契约，在结束时统一检查轨迹、diff 和证据；除阻塞或安全问题外，不用连续微提示把模型
推过实现细节。

## Gate 1：设计准入

新增产品能力、公开 API、持久化状态、Sidecar 资源或 Feature Flag 前，必须能回答：

1. 哪个真实任务失败了，或哪个安全边界无法成立？
2. 失败轨迹、用户反馈或当前代码证据在哪里？
3. 上游优先实现阶梯逐层调查了什么，为什么更早的层级不能解决？
4. 最小可交付纵切是什么，用户能看到什么不同？
5. 哪个真实任务、权威回执或独立 Judge 能判定成功？
6. 如果没有产生预期收益，删除点和退出条件是什么？

不能回答以上问题时，只能形成简短研究结论、原型或隔离实验，不能提前增加产品状态机、设置、
兼容层、隐藏入口或完整纵切。

以下情况不需要等待产品失败轨迹，但仍应实现最小边界：

- 修复已复现缺陷；
- Credential、Scope、路径、私有远端、Judge 或不可逆外部效果风险；
- 当前纵切无法继续或已有验收会失真；
- 用户明确要求的当前产品结果。

## Gate 2：开发边界

实现已准入纵切时：

- 直接实现当前干净模型，不为废弃的 pre-release 设计添加 migration、dual-write、fallback、
  legacy adoption 或兼容分支；
- 不为“以后可能需要”预建 Provider、角色、工作流、连接器、状态枚举或 UI；
- Feature Flag 只用于正在交付能力的短期风险控制，必须有当前负责人、验收条件和删除时机；
- Paused 能力只保留设计摘要，不应继续进入 release 构建、默认启动或用户产品面；
- 实验代码必须位于独立 CLI、测试目录或不参与 release 的明确构建目标；
- 新 Wails API 和 Sidecar 文件必须有真实产品调用者，不能只服务 smoke、fixture 或未来设计；
- 触碰热点文件时遵守既定依赖方向，避免继续增加新的职责，但不另开无产品结果的架构清理里程碑。

“默认关闭”不等于已经隔离。只要代码仍被打包、注册、初始化、暴露或要求维护兼容，它就是产品
成本。

## Gate 3：测试与验收边界

测试应观察产品，不应成为产品的一部分：

- Go fixture 放在 `_test.go`、`testdata/` 或独立测试包；
- 前端 mock 和 story 不从 `App.vue` 或其他生产入口导入；
- 正式 Wails bindings 不暴露仅供测试使用的 `Smoke`、`Fixture` 或 `Sample` 方法；
- 启动路径和 Vue lifecycle 不运行测试协调器，即使它通常因环境变量而空操作；
- Browser preview 可以展示静态组件状态，但不能伪造完整领域后端或持久化状态机；
- benchmark 应调用生产 Runtime 的正式接口，不维护第二套 Agent Runtime；
- 测试需要的产品操作应通过正常产品 API 完成，缺少可测性时优先改善真实接口边界。

验收结论按证据强度表述：

| 证据 | 可以声明 | 不可以声明 |
| --- | --- | --- |
| Unit / Component test | 局部规则或组件行为通过 | 真实产品任务完成 |
| Fixture / smoke | 固定路径在限定环境可复跑 | Provider、完整 Harness 或用户流程已验证 |
| 打包 App / WebView 验收 | 明确记录的原生纵切可用 | 相邻能力、跨平台或长期可靠性完成 |
| 真实任务 + 实际回执 | 该任务及记录范围内已验证 | 未覆盖场景自动成立 |
| 独立 Judge / 明确人工结果 | 对应候选成功或失败 | 模型自己的成功声明成为事实 |

按钮、包、工具消息、环境已开启、生成了 Projection 或 Agent 自述成功，都不能单独建立完成事实。

## Gate 4：评审、交付与保留

代码评审和交付收口时必须检查：

- 本批次新增了哪些生产依赖、Wails API、Sidecar 文件、schema 和用户入口？
- 是否出现只有测试、预览、研究或未来设计使用的正式代码？
- 是否重复了 Pi 或已审阅上游资源的行为？
- 是否保留了旧 pre-release 模型的兼容路径？
- 真实任务结果、失败分类和人工接管次数是否支持保留这项能力？
- Feature Flag、实验入口和临时代码是否已删除，或具有明确的当前退出条件？

`Implemented / unverified` 只能是有时限的实验状态，不能成为永久产品层。到约定的验收批次仍
没有真实任务收益时，默认从产品链删除；需要时可以保留简短研究结论和复现材料。

删除应优先随所触碰的产品纵切完成。只有跨多个持久化 schema 的 pre-release 清理，才集中为
一次明确、破坏性、完整回归的 consolidation。

## Pre-release 数据规则

- schema 与当前模型不兼容时，明确拒绝、重建或要求用户重置，不静默迁移；
- Provider Credential 不读取旧明文字段再迁移，必须重新授权或重新填写；
- 不为未发布数据增加长期版本升级框架；
- 备份、导出和恢复负责用户数据安全，不代表必须兼容旧 schema；
- 已工作的旧 schema 按当前目标约定，等待一次有边界的最终破坏性 consolidation，不在无关
  功能纵切中顺手迁移。

## PR 最小检查表

涉及产品能力或 Harness 的 PR 描述应简短回答：

```text
真实失败轨迹或安全边界：
用户可见结果：
当前完成条件：
上游能力调查：
采用的实现阶梯层级与未采用上一层的原因：
新增生产 API / schema / Sidecar 文件：
测试是否进入生产依赖图：
真实验收证据：
未产生收益时的删除点：
```

纯文档、机械重命名和不改变产品行为的小修可以注明“不适用”，不需要制造虚假证据。

## 一句话原则

MilkSU 产品代码只承载当前用户价值、不可替代的桌面安全边界和 MilkSU 独有领域事实；实验、
证明和未来可能性不能获得产品链的永久居留权。
