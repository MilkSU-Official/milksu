## 怎么填写

不必一次填完，也不必为每一行写意见。优先填写你最在意或最想调整的部分：

- **大任务决定：** 可填“保留 / 拆分 / 合并到…… / 后置 / 暂停 / 删除”；
- **优先级：** 可填 `P0 / P1 / P2 / 后期`，也可以直接写自然语言；
- **小任务决定：** 可填“保留 / 修改 / 合并到…… / 后置 / 删除”；
- **新增项：** 在每个大任务后的新增区继续添加，不需要自己分配正式 ID；
- **备注：** 可以写产品直觉、使用场景、验收想法、担忧或“不懂这项有什么用”。

填写规则：

1. 空白表示“暂时没有意见”，不是同意或删除；
2. 修改已有小任务时保留它的 ID，方便和证据台账对照；
3. 你写的内容不会自动触发开发、审批、外部发布或真实平台操作；
4. 我重新读取后会先复述你的改动，并把含糊项转成可验收事项，再请你确认开发批次；
5. 详细实现证据和“还缺什么”不在本文件重复维护，避免两份事实源漂移。

### 总体方向

1. **先做能够长时间自主工作的产品，而不是先补齐审批矩阵。** Coding Agent 的核心结果是
   持续执行真实任务、产出用户想要的功能、自动构建、测试和交付。
2. **默认优先“替我审批”和“完全访问”的顺畅体验。** “请求批准”的完整组合矩阵和审批
   细节后置，不让普通、已授权、可恢复的操作反复打断用户。
3. **功能广度优先采用成熟组件。** ImageGen、Browser、MCP、Skill 和 Plugin 尽量集成
   固定版本、可审阅的成熟实现，不从头自研相同能力。
4. **CTF 先作为并行验收活动展开。** 六个赛道分别运行、保留材料和 Judge 证据、反馈问题；
   发现缺口先进入台账，不在单题里无限深挖。
5. **Memory 先做直接影响体验的部分。** 大规模归属校准和追求完美的统计模型后置。
6. **Runtime 只保留支撑真实产品的关键项。** App 重启和长任务恢复并入 Coding 自主执行；
   NYU Outcome Bench 后置。
7. **架构不做独立清债冲刺。** 功能稳定并经过用户测试后再集中收口，但当前修改不能继续给
   热点文件增加新职责或制造明显的一次性技术债。
8. **发行门禁后置。** Developer ID、Hardened Runtime、公证、升级和新机器矩阵等到准备
   外部版本时再做。
9. **文档分两层。** 每个任务只更新测试、回执和必要验收记录；架构、里程碑、状态和发布
   说明继续留到最后统一更新。

### 必须保留的最小硬边界

“不追求完美的安全边界”解释为不优先完善所有审批组合和边角交互，不解释为取消以下底线：

- Provider Credential 不进入模型上下文、终端、日志、诊断包或普通迁移；
- 不向引用的开源项目发布 PR，只允许 MilkSU 明确授权的私有远端；
- 付费、外部账户授权、扩大网络或应用 Scope、托管平台发布仍需要有意义的一次确认；
- 文件路径、项目边界和精确 Endpoint 不能因为“完全访问”而逃逸；
- 用户没有要求的删除、覆盖和不可逆外部操作不能静默执行。

这些是少量不可绕过的产品不变量，不要求现在扩展成复杂的逐工具审批工作流。

### 建议重新组织优先级

| 建议层级 | 包含内容 | 为什么 |
| --- | --- | --- |
| P0 · 自主工作主线 | Coding 的修改、构建、测试、预览、替我审批、完全访问、Compaction，以及完整 App 重启和长任务恢复 | 直接对应“连续跑很久不用用户管” |
| P1 · 成熟能力集成 | ImageGen、真实 Project MCP、Browser/前端 Skill，以及由真实高频需求选出的 Plugin | 能较快扩大能力面，但每项仍需一个真实任务证明可用 |
| P1 · CTF 广度验收 | 六赛道分别运行，包含一次 Tool Builder 和一次 Strategist 协作 | 主要产生真实验收证据和问题清单，不混入无限修复 |
| P2 · Memory 用户体验 | 推荐理由可追溯、Memory 与能力画像可理解、删除后结果一致 | 用户能直接感知；36 条完整校准矩阵后置 |
| 持续约束 | 触碰即拆、边界不反向依赖、验收证据更新 | 不单独占用一个重构周期 |
| 后期 | NYU Outcome、完整请求批准矩阵、pre-release 破坏性收口、签名、公证、升级、最终文档 | 当前不直接提高核心使用体验 |

### 当前仍需注意的取舍

- “集成开源组件”能减少自研和组件级测试，但不能省略 MilkSU 的权限适配、打包兼容和一个
  真实任务验收；否则只能证明组件存在，不能证明用户能用。
- “堆积功能”建议解释为扩大有用能力覆盖，而不是增加按钮数量。每项能力至少要完成一个
  用户目标，否则不计入替代率。
- CTF 可以由不同 subagent 分赛道执行，主 Agent 仍负责授权边界、证据审阅、问题去重和
  最终汇总；外部 Judge 或用户条件不足时应明确停在“未验收”。
- “不留技术债”与“架构以后再说”不能同时按绝对含义满足。可执行版本是：现在不做纯重构，
  也不新增明显错误职责；功能稳定后再集中整理已有热点。

## 一轮填写后的处理方式

用户完成任意一轮填写后，主 Agent 只做以下工作，不直接开发：

1. 读取本文件中所有 `USER-REVIEW` 区域和表格备注；
2. 列出新增、删除、合并、优先级变化和仍有歧义的事项；
3. 对照当前仓库与覆盖台账，指出哪些想法已经实现、哪些需要用户条件、哪些可独立准备；
4. 给出一个或多个有边界的候选批次，每批写明价值、风险、依赖、验收和禁止顺带修改范围；
5. 只有用户明确选定批次后，才恢复该批次的开发。

多轮评估期间，本工作簿是共同讨论区；`current-objectives.md` 仍是范围契约，
`objective-coverage-ledger.md` 仍是证据和百分比事实源。
