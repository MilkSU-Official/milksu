## 先说结论

安全 Agent 和通用代码 Agent 在“思考和干活的能力”上高度重叠。架构设计、写代码、测试、调试、搜索、逆向、写脚本，本来就是通用研发能力。上游模型越强，这部分重叠越大。

讨论 MilkSU 时，需要分别回答三个问题：

| 问题 | 人话解释 | 对应架构 |
|------|----------|----------|
| Agent 自己会不会被外部内容或工具攻击？ | 例如网页中的 prompt injection 诱导 Agent 泄露数据 | Agent Security / Integrity Layer |
| Agent 最终要完成什么安全结果？ | 例如红队要证明攻击路径，蓝队要完成遏制与恢复 | Role Package（角色包） |
| Agent 靠什么技术完成任务？ | 例如二进制逆向、Web 测试、取证或移动端分析 | Capability Package（能力包） |

其中：

- **Role Package（角色包）**决定“这场任务怎样才算赢”。
- **Capability Package（能力包）**决定“可以用哪些方法和工具去做”。
- **Agent Security（Agent 自身安全）**决定“执行过程中怎样保护 Agent、凭据和数据”。

这三者可以自由组合。二进制逆向不是 AppSec 独占的角色，而是一种可以被红队、CTF、恶意样本分析和漏洞研究共同使用的能力。

## Agent Security 和 Agent for Security 不是一回事

### Agent Security：保护 Agent 自己

这里的“安全”描述的是 Agent 的运行方式，而不是它正在做什么任务。

例如：

- 网页正文里藏着 prompt injection（把恶意指令伪装成普通内容）。
- 某个插件或 Skill 偷偷读取不该读取的凭据。
- 工具返回值诱导 Agent 把内部数据发送到外部地址。
- 恶意文件利用分析工具本身的漏洞。

这些风险同样会出现在浏览、邮件、办公和代码开发 Agent 中，所以不能算作安全任务 Agent 的独有能力。

### Agent for Security：用 Agent 做安全任务

这里的“安全”描述的是任务目标。例如：

- 红队在授权范围内证明某条攻击路径成立。
- 蓝队从日志和主机证据中判断是否发生入侵并完成处置。
- CTF Agent 解出题目并让 judge（自动判题程序）接受 flag。
- AppSec Agent 复现漏洞、生成补丁并跑回归测试。

![Agent Security 与 Agent for Security 的二轴分类](/agent-security-vs-security-agent.svg)

图里最重要的两个例子是：

- 普通 CTF Agent 正在做安全任务，但可以运行在隔离、可重置的环境中，不一定有人正在攻击这个 Agent。
- 普通浏览或邮件 Agent 没有做安全任务，却可能非常需要 prompt injection 和数据外传防护。

### 对上一版表述的修正

上一版写过“安全 Agent 必须默认任意输入都可能被攻击者控制”。这句话把两类问题混在了一起，不能作为统一架构前提。

更准确的说法是：

- 任何读取不可信内容的 Agent 都需要输入完整性保护，不限于安全领域。
- 红队目标可能部署 honeypot（故意引诱攻击者的假目标）、EDR（终端检测与响应系统）或欺骗机制，但这是特定环境中的防守响应，不是所有红队任务的定义。
- 蓝队确实会读取攻击者可能影响的日志、文件和流量，但“这些内容可能 prompt inject LLM”是引入 Agent 后新增的运行安全问题，不是蓝队任务本身的核心。
- 普通 CTF 一般是隔离解题；attack-defense CTF（队伍之间同时攻击和防守）才具有持续对抗状态。

所以，外部内容防护应放在跨领域的 Agent Integrity Layer（Agent 完整性层），不能当作安全任务的专属护城河。

## 角色和能力不是一回事

可以把角色理解为“比赛规则和计分板”，把能力理解为“工具箱”。

### 二进制逆向属于共享能力

二进制逆向包括反汇编、反编译、动态调试、符号恢复、控制流分析和模拟执行。它回答“怎样理解这个程序”，但没有单独规定“理解以后要达成什么结果”。

同一套二进制能力可以服务不同角色：

| 使用场景 | 角色 | 最终怎样才算完成 |
|----------|------|------------------|
| 分析程序漏洞，生成 PoC 和补丁 | AppSec / 漏洞研究 | 漏洞可复现，补丁能阻断漏洞且回归测试通过 |
| 逆向题目寻找 flag | CTF | judge 接受 flag |
| 分析恶意程序行为 | 蓝队 / 恶意样本分析 | 行为链、IOC 和检测规则得到证据验证 |
| 逆向目标服务并构造利用 | 红队 | 攻击路径和实际影响得到证明 |
| 分析固件、协议或闭源产品 | 产品安全 / 漏洞研究 | 攻击面、安全属性或漏洞得到验证 |

这里的几个词：

- **PoC（概念验证程序）**：用最小代码证明漏洞确实存在。
- **回归测试**：确认修复漏洞以后，原功能没有被破坏，而且漏洞不能再次触发。
- **IOC（入侵指标）**：可以帮助识别攻击的文件哈希、域名、进程行为等线索。

因此，MilkSU 应提供共享的 `Binary Analysis Capability`，再由不同角色包决定状态、证据和判分方式。

### 其他能力也应这样理解

| 能力包 | 提供什么 | 可以服务哪些角色 |
|--------|----------|------------------|
| Binary Analysis | 反编译、调试、模拟执行、控制流和数据流分析 | Red、CTF、AppSec、Malware、漏洞研究 |
| Web Security | 浏览器、代理、请求重放、会话和 API 分析 | Red、CTF、AppSec |
| Network Security | 扫描、抓包、协议分析和网络位置管理 | Red、Blue、CTF |
| Mobile Security | APK、IPA、设备、Hook、移动端流量分析 | Red、AppSec、CTF、漏洞研究 |
| Forensics | 镜像、日志、时间线、文件和内存证据分析 | Blue、恶意样本分析、事件响应 |
| Fuzzing | 自动生成输入、收集崩溃并最小化样本 | AppSec、漏洞研究、CTF |

能力包可以共享工具和操作方法，但不能替角色包宣布任务成功。

## 不同角色各自需要什么

“世界状态”是 Agent 对当前真实情况的结构化记录。例如红队已经拿到哪些凭据、蓝队目前有哪些证据。它不能只藏在一段聊天历史里，否则模型切换或进程重启后就会丢失。

“Evaluator（判分器）”是不听模型自评、独立检查任务是否成功的程序或规则。例如 flag 提交器、PoC 测试或补丁回归测试。

| 角色 | 它要解决什么 | 必须持续记住什么 | 谁来判断成功 |
|------|--------------|------------------|----------------|
| 红队 / Pentest | 在授权范围内证明攻击路径和影响 | 资产、身份、凭据、可达性、当前权限、已执行动作和清理状态 | 目标状态变化、权限证明或可复现影响 |
| 蓝队 / DFIR / SOC | 从不完整证据中发现、限制并恢复安全事件 | 时间线、实体关系、多个可能解释、置信度、处置和业务影响 | 检测结果、人工复核、遏制与恢复结果 |
| CTF | 在规则和隔离环境内得到正确答案 | 题目、假设、失败原因、脚本和环境快照 | flag 提交器或其他 judge |
| AppSec | 发现、复现和修复软件安全缺陷 | 代码路径、PoC、受影响版本、补丁和回归结果 | PoC、补丁验证和测试套件 |
| Malware Analysis | 解释恶意程序做了什么，并形成检测或处置依据 | 样本来源、行为、配置、基础设施、IOC 和分析环境 | 沙箱结果、人工分析、检测规则或事件证据 |
| Vulnerability Research | 研究产品或固件的攻击面和未知漏洞 | 版本、目标组件、假设、崩溃、根因、利用条件和披露状态 | 可重复触发、根因证据和影响验证 |

`DFIR` 是数字取证与事件响应，`SOC` 是安全运营中心。它们都属于蓝队，但侧重点不同。

### 红队：维护一场受约束的攻击过程

红队的重点不是“面对恶意输入”，而是安全地推进授权攻击路径：

- `Scope`（授权范围）：允许测试哪些目标、时间段和动作。
- `AttackGraph`（攻击图）：从当前位置到目标权限之间有哪些路径。
- `CapabilityState`（当前能力状态）：已经拥有哪些身份、凭据和网络位置。
- `EffectLedger`（副作用账本）：哪些动作改变了目标系统，是否需要回滚或清理。
- `ProofOfImpact`（影响证明）：用外部证据证明控制权、可达性或业务影响，而不是只相信模型说“成功了”。

### 蓝队：维护证据、假设和处置状态

蓝队要处理的信息经常不完整、延迟甚至互相矛盾：

- `EvidenceGraph`（证据图）：哪些用户、主机、进程、文件和网络事件彼此相关。
- `HypothesisSet`（竞争假设集合）：同时保留“真入侵”“误报”“内部操作”等解释，而不是过早锁定一个答案。
- `Confidence`（置信度）：当前证据对每个解释的支持程度。
- `Provenance`（来源记录）：每条证据来自哪里、何时收集、有没有被修改。
- `Chain of custody`（证据保管链）：谁在什么时候接触和处理过证据，保证调查过程可审计。
- `ResponseState`（处置状态）：哪些主机已隔离、哪些账号已冻结、业务是否恢复。

蓝队的差异化来自证据推理、案件管理和安全处置，不是“日志会攻击 LLM”。

### CTF：维护可重复的解题实验

普通 CTF 更像一个带自动判题的实验任务：

- `ExperimentTree`（实验树）：尝试过哪些思路，为什么失败，下一步从哪里继续。
- `Snapshot`（环境快照）：保存或恢复某个确定的环境状态。
- `Judge`（判题器）：检查 flag 或输出是否正确。
- `success@N`：最多允许尝试 N 次时，至少成功一次的任务比例。

对于单道题，强通用 Agent 很可能已经足够。MilkSU 的额外价值主要出现在批量测试、环境变体、失败轨迹复用和成本比较。

### AppSec：连接漏洞、补丁和回归

AppSec 与普通代码开发重叠最大。需要增加的是安全验证闭环：

- `Source-to-sink`（从输入源到危险操作的数据路径）：外部输入怎样到达命令执行、SQL 查询或内存写入等位置。
- `Taint`（不可信标记）：记录某个数据是否来自外部输入，以及它传播到了哪里。
- PoC 与真实漏洞状态之间的验证。
- 原始 PoC、绕过变体、补丁和回归测试的联动。
- 跨版本、架构和配置的适用范围。

AppSec 不应重造一套完整 Coding Agent，而应在强代码 Worker 外增加漏洞验证、补丁和回归判分器。

### 恶意样本分析和漏洞研究：按结果决定是否独立成角色包

它们经常使用二进制逆向，但目标与 AppSec 不完全相同：

- 恶意样本分析关心行为、基础设施、IOC、检测和处置。
- 漏洞研究关心崩溃、根因、利用条件、影响范围和负责任披露。

MilkSU 不必一开始就为每个名称创建独立模块。只有当它们拥有明显不同的长期状态和 evaluator 时，才值得升级为独立 Role Package；否则可以先作为任务模板使用共享能力包。

## 通用 Agent 会覆盖哪些部分

`SOTA` 指当前能力最强的一代基础模型。新 SOTA 会让下面这些能力越来越通用：

- 阅读代码、二进制和协议。
- 编写扫描器、PoC、调试脚本和测试工具。
- 搜索资料、提出假设、规划步骤和总结结果。
- 调用编译器、调试器、浏览器、反编译器和抓包工具。

![通用 Agent 与角色特定安全闭环](/security-agent-boundary.svg)

图中的蓝色范围会随着模型增强继续扩大。二进制分析、代码审计和安全工具开发等共享能力主要位于这个重叠区，不归某一个角色独占。橙色部分是当前仍需要安全知识或推理、但未来可能被模型吸收的能力。绿色部分用四个角色举例表示各自的环境、状态和判分闭环，更不容易因为换模型而消失。

### 容易被新模型替代的工程

- Prompt 技巧和“安全专家人格”。
- 把固定步骤硬编码成工作流。
- 只负责拆任务的泛化多 Agent 角色。
- 只是把通用工具包一层接口的薄封装。

它们现在可能有用，但更像是在弥补这一代模型的不足。

### 能与新模型互补的工程

“互补”表示模型越强，这些资产越容易发挥价值，而不是被替代：

- 真实环境的稳定接入、快照、重置和清理。
- 独立判分器和经过校准的成功标准。
- 跨运行保存的角色状态、证据和副作用记录。
- 可以重放、比较和学习的真实任务轨迹。
- 红队、蓝队、CTF、AppSec 等不同角色的专用闭环。

判断方法很简单：

> 如果下一代模型拿到仓库和 API 文档后，很快就能重新实现它，它通常不是长期护城河。

真正耐模型升级的资产，多半依赖长期环境、真实数据、组织授权、角色状态和可靠判分器。

## Agent Security 仍然重要，但它是共享层

MilkSU 会操作浏览器、工具、凭据和外部内容，所以仍然需要 Agent Integrity Layer：

- `Instruction / Content Separation`：区分用户真正下达的指令和网页、邮件、日志中的普通内容。
- `Observation Provenance`：记录每条工具结果或观察来自哪里。
- `Taint Tracking`：给不可信数据加标记，并跟踪它流向了什么工具或输出。
- `Sandbox`（沙箱）：把恶意文件或高风险程序限制在隔离环境中运行。
- `Credential Isolation`（凭据隔离）：让 Agent 只能在需要时使用指定凭据，不能随意读取和外传。
- `Capability Policy`（工具权限策略）：明确某个 Agent 可以调用哪些工具、访问哪些目标。
- `Egress Policy`（外传策略）：限制数据能发送到哪些外部地址。
- `Supply-chain Security`（供应链安全）：检查插件、Skill、MCP 和依赖是否可信。

这层可以保护普通办公 Agent、开发 Agent 和安全任务 Agent。它很重要，但不能被宣传成 Agent for Security 的独有长板。

## 对 MilkSU 的直接指导

### 推荐分层

~~~text
Desktop / CLI / API
        |
Role Packages
Red / Blue / CTF / AppSec / Malware / Vulnerability Research
        |
Capability Packages
Binary / Web / Network / Mobile / Forensics / Fuzzing
        |
Shared Security Substrate
Environment / Evaluator / Evidence / Trace / Effect
        |
General Worker
Pi / Codex / Claude Code / 其他模型和工具

Cross-cutting Agent Integrity
Provenance / Sandbox / Credential / Capability / Supply Chain
~~~

每层的人话解释：

1. **General Worker**：真正调用模型、写代码和使用工具的执行器，应该尽量薄，方便直接更换成新 SOTA。
2. **Shared Security Substrate（公共安全底座）**：保存运行、环境、证据和结果的通用机制，不替任何角色决定业务含义。
3. **Capability Package**：跨角色共享的工具箱，例如 Binary、Web 和 Forensics。
4. **Role Package**：定义目标、长期状态、动作含义和 evaluator，回答“怎样才算完成”。
5. **Agent Integrity**：按实际内容信任度和权限风险横切保护整个执行过程，不与某个安全角色绑定。

### 公共底座需要保存什么

- `Run`：一次完整任务运行。
- `Step`：任务中的一个阶段或动作。
- `ToolCall / ToolResult`：调用了什么工具，得到了什么结果。
- `Artifact`（工件）：运行产生的文件、日志、PoC、补丁、抓包或报告。
- `Evaluation / Outcome`：判分过程和最终结果。
- `Trace`（轨迹）：按时间串起模型调用、工具动作、证据和结果的完整记录。
- `Replay`（重放）：在相同条件下重新执行或检查一段轨迹。
- `Effect`（副作用）：任务对外部系统造成的变化，例如创建账号、隔离主机或写入文件。

### Role Package 最少需要声明什么

1. **Role**：服务什么角色，最终 outcome（任务结果）是什么。
2. **Environment**：目标、资源、版本、快照、重置和清理方式。
3. **Capabilities**：需要哪些能力包，而不是把所有工具复制进角色包。
4. **Actions**：动作的输入输出、风险、副作用、前置条件，以及重试是否安全。
5. **Evaluator**：成功、失败和部分成功怎样判断。
6. **State Projection**：怎样从通用事件生成角色视图；简单说，就是怎样把原始日志整理成攻击图、案件时间线或实验树。
7. **Evidence Schema**：每个结论必须由哪些工件或观察支撑。
8. **Benchmark Cases**：用于重复比较的固定任务、预算、环境版本和期望结果。
9. **Integrity Requirements**：它会读取哪些不可信内容、使用哪些凭据，需要什么 Agent Security。
10. **Prompt / Guidance**：给模型的提示和策略，只能作为可替换建议，不能作为事实来源。

`Benchmark` 是固定的测试题集和测量方法。它的作用是让不同模型、Prompt 或 Skill 的效果可以公平比较，而不是只看一次演示是否成功。

## 一个模块要不要进入 MilkSU 核心

依次问下面这些问题：

1. 它解决的是 Agent 自身安全，还是用 Agent 做安全任务？
2. 如果是安全任务，它服务什么角色，怎样才算完成？
3. 它是角色包还是能力包？会不会把“使用某种工具”误当成一个角色？
4. 它是在弥补当前模型，还是保存模型外部的环境、状态和判分能力？
5. 换成新 Worker 后，它能不能原样复用？
6. 有没有独立于模型自评的 evaluator？
7. 有没有留下可重放、可比较的 trace 和 artifact？
8. 它能否提高成功率、降低单次成功成本、减少误判、改善恢复或控制副作用？

如果价值主要来自 Prompt、角色人格或固定步骤，先放在实验层。如果价值来自真实环境、能力接入、角色状态、可靠判分器、证据和历史轨迹，才适合进入核心。

## 可跳过的技术附录：集合模型

<details>
<summary>展开数学表达和符号解释</summary>

定义：

- `U(M)`：模型能力为 `M` 时，通用 Agent 能稳定完成的任务集合。
- `S_r`：角色 `r` 的全部安全任务，例如 `S_red` 或 `S_blue`。
- `D_r(M) = S_r - U(M)`：这个角色中，当前通用 Agent 还不能稳定覆盖的部分。

随着模型增强，通用能力集合会扩大：

~~~text
U(M1) subset U(M2) subset U(M3)
~~~

角色的剩余差异可以写成：

~~~text
D_r(M) = K_r(M) union O_r

K_r(M): 当前模型还没有掌握好的角色知识和推理
O_r:    角色特定的环境、长期状态、判分和副作用语义
~~~

`K_r(M)` 会随模型增强而缩小。`O_r` 不完全依赖模型智力，所以更耐模型升级。

Agent 自身安全属于另一组正交基础设施：

~~~text
G = Agent Integrity + Sandbox + Credential Isolation
    + Generic Recovery + Supply-chain Security
~~~

`G` 很重要，但它不属于 `O_red`、`O_blue`、`O_ctf` 或 `O_appsec` 的专属差异。

</details>

## 最终原则

> 新 SOTA 发布时，MilkSU 应优先替换 General Worker，然后重新运行各角色 benchmark。角色包、能力包、环境、判分器、证据和历史轨迹应当继续复用。

安全 Agent 不是一种统一、永久领先于通用 Agent 的智能。MilkSU 真正要建设的是：让强通用 Worker 能够接入共享安全能力，并在不同角色的真实环境中形成可验证、可恢复、可积累的任务闭环，同时不把 Agent 自身安全误当成安全任务的定义。
