架构设计文档 -- 基于 Codex CLI 开源代码的复用分析与 MilkSU 适配设计

0. Codex CLI 开源全景

先回答核心问题：Codex CLI 开源意味着什么？

Codex（github.com/openai/codex）是 OpenAI 的编码 Agent，Apache-2.0 开源，94k stars。关键认知：它不是一个简单的 CLI 封装，而是一个完整的 Agent 引擎，用 Rust 写了约 80+ 个 crate。

代码库结构总览

目录/Crate 功能 对 MilkSU 的价值
codex-rs/core Agent 核心循环：会话管理、上下文构建、工具调度 高：原理可学
codex-rs/sandboxing 跨平台沙箱：bubblewrap (Linux) / Seatbelt (macOS) / Windows Sandbox 极高：直接参考
codex-rs/execpolicy 命令权限引擎：Starlark 规则语言，prefix matching，allow/prompt/forbidden 三级决策 极高：可移植
codex-rs/linux-sandbox Linux 沙箱细节：bubblewrap + seccomp + Landlock 高：实现参考
codex-rs/memories 两阶段记忆流水线：rollout 提取 + 全局合并 高：架构参考
codex-rs/thread-store 会话持久化：ThreadStore trait + JSONL + SQLite 中：我们已有 JSON 方案
codex-rs/hooks 生命周期钩子：Pre/Post tool use, Stop, Notification 高：设计参考
codex-rs/skills 技能系统：类似 Pi 的 SKILL.md 中：我们用 Pi 原生系统
codex-rs/shell-escalation Shell 命令提权检测 高：安全工具必需
codex-rs/tui 终端 UI：Ratatui TUI 渲染 低：我们用 React GUI
codex-rs/mcp-server MCP 服务端/客户端实现 中：Pi 已有 MCP 支持
codex-rs/core-plugins 内置插件系统 高：设计参考
核心结论：Codex 的代码库分层非常清晰 -- 引擎层（core, sandboxing, execpolicy, memories）和展示层（tui, cli）完全解耦。引擎层的设计和实现可以直接学习，因为 Agent 引擎的核心问题（沙箱隔离、权限决策、记忆持久化、会话管理）与展示形态无关。CLI 和 App 的区别只在于"用户怎么看到结果"，而不在于"引擎怎么运行 Agent"。

2. 可直接复用 vs 需重新设计

可直接复用的（原理相同，实现可参考）

Seatbelt 沙箱（macOS）

Codex 的 sandboxing/seatbelt.rs 使用 macOS 原生的 sandbox-exec 命令和 SBPL（Sandbox Profile Language）策略文件。这是 macOS 上最轻量的沙箱方案，比 Docker 快几个数量级。MilkSU 的 Rust 后端可以直接实现相同的 Seatbelt 集成。

Codex 文件：sandboxing/seatbelt_base_policy.sbpl, seatbelt_network_policy.sbpl

execpolicy 规则引擎

Codex 用 Starlark 语法定义命令权限规则（prefix_rule()），这套"命令前缀匹配 + 三级决策"的模型与 MilkSU 的安全工具场景完美匹配。我们可以用同样的规则语言，只是规则内容不同（安全工具 vs 编码工具）。

Codex 文件：execpolicy/src/*, execpolicy/README.md

Shell 提权检测

Codex 的 shell-escalation crate 检测 shell 命令中的提权行为（sudo、chmod、chown 等）。对安全工具平台来说这更重要 -- 我们需要区分"正常的安全工具调用"和"意外的提权企图"。

Codex 文件：shell-escalation/src/*

记忆流水线架构

Codex 的两阶段记忆（Phase 1: 逐个会话提取 -> Phase 2: 全局合并）是一个成熟的异步流水线设计。我们的 Engagement Memory 可以借鉴同样的架构：工具结果提取 -> Engagement 合并 -> 知识库提炼。

Codex 文件：memories/read/*, memories/write/*

需要重新设计的（场景不同，原理可学）

子 Agent 系统

Codex 的子 Agent 面向"代码编辑"（并行修改不同文件），MilkSU 面向"安全测试"（并行扫描不同目标）。协调模式完全不同：Codex 需要文件锁和 git worktree 隔离，MilkSU 需要网络隔离和结果汇总。

权限决策的数据源

Codex 的权限决策基于"命令是否安全"（文件操作 vs shell 命令）。MilkSU 的权限决策需要额外维度："目标是否授权"、"沙箱等级是否足够"、"当前 engagement 是否 active"。

浏览器/Computer Use

Codex CLI 没有浏览器集成。这是 MilkSU 作为 GUI App 的独特优势 -- 我们可以内嵌 WebView、集成 CDP、提供 Computer Use 能力。这部分需要从 Claude Code / Anthropic Computer Use 的方向参考。

数据模型

Codex 的记忆内容是通用文本（代码修改摘要、开发者偏好）。MilkSU 的记忆是强结构化的安全数据（Host/Service/Vulnerability/Credential）。数据模型需要完全自己定义。

面试知识点 -- 开源复用策略：复用开源代码有三个层次：代码级复用（直接引用/fork 源码）、架构级复用（学习设计模式和分层方式）、概念级复用（借鉴解决问题的思路）。对 MilkSU 来说，Codex 主要提供架构级和概念级复用。代码级复用受限于语言（Codex 的引擎是 Rust，MilkSU 的 Agent 逻辑在 TypeScript/Pi 层；但 Rust 后端可以参考 sandboxing crate）。判断复用层次的关键问题："问题域是否相同？"相同则可代码级复用（沙箱 SBPL），不同则只能架构/概念级复用（记忆系统）。

3. 为什么安全场景需要子 Agent

单个 Agent 在安全测试中会遇到两个瓶颈：

瓶颈一：串行等待

nmap 全端口扫描一台主机需要 2-5 分钟。扫描 10 台主机串行执行需要 20-50 分钟。用户盯着进度条看半小时，而其中每次扫描之间没有任何依赖关系。

瓶颈二：上下文污染

渗透测试是一个"分支探索"过程 -- 发现 5 个潜在入口后，需要分别深入测试每一个。如果单个 Agent 串行处理，越往后上下文越长，LLM 的注意力被稀释，容易"忘记"早期发现或混淆不同目标的信息。

子 Agent 的本质：不是"多个 AI 同时聊天"，而是将一个复杂任务分解为独立子任务，在各自隔离的上下文中并行执行，最后汇总结果。每个子 Agent 有自己的 LLM 上下文窗口、工具调用权限、沙箱环境。

安全场景的典型并行模式

场景 主 Agent 任务 子 Agent 任务 并行度
多目标扫描 协调扫描范围，汇总发现 每个子 Agent 扫描一个 IP 段或主机 按目标数量
多维度侦察 选择目标，综合评估 分别执行端口扫描、DNS 枚举、Web 目录爆破、子域名发现 按工具维度
漏洞验证 收集候选漏洞列表，确认结果 每个子 Agent 验证一个候选漏洞（尝试利用 + 判断是否成功） 按漏洞数量
密码爆破 选择目标服务，收集凭证 分别对 SSH、FTP、MySQL、RDP 等服务执行字典爆破 按服务数量
CTF 解题 分析题目，分配方向 分别尝试不同解题思路（逆向、Web、Crypto 方向） 按思路数量

4. 行业子 Agent 方案对比

平台 并行度 隔离方式 协调模式 通信机制
Codex 最多 6 个并发 git worktree（文件隔离） 主 Agent 分发任务，子 Agent 返回结果 线程内消息传递
Claude Code 5 层嵌套 + Workflow worktree + 独立上下文 Agent 工具调用（递归）或 Workflow 脚本编排 工具调用返回值
Arkloop 不限（受资源限制） 每个 Agent 独立 Firecracker VM API 编排（Go 微服务协调） ACP 协议 + PostgreSQL 共享状态
Memoh 不限（每 Agent 一个容器） 每个 Agent 独立 Docker 容器 外部触发（Telegram/Discord 消息） 共享记忆（Mem0）+ 渠道消息

Codex 的子 Agent 实现细节

从 Codex 的 thread-store 和 thread-manager-sample 源码可以看出：

  • ThreadStore trait：定义了 append_items（追加历史）和 update_thread_metadata（更新元数据）两个核心 API。每个子 Agent 就是一个独立的 thread。
  • LiveThread：活跃会话的封装，管理元数据同步、rollout 持久化策略、历史追加。子 Agent 的会话生命周期由 LiveThread 管理。
  • ThreadManager：路由器，管理加载和冷冻的 thread。主 Agent 通过 ThreadManager 创建和管理子 Agent thread。
  • 隔离：使用 git worktree 让每个子 Agent 在独立的文件系统副本上工作，避免并行写入冲突。
关键差异：Codex 的子 Agent 隔离是文件系统级的（git worktree），因为编码场景的冲突在文件修改上。MilkSU 的子 Agent 隔离需要是网络级的（每个子 Agent 的沙箱只允许访问各自的目标），因为安全场景的冲突在网络访问上。但上层的编排模式（ThreadManager -> 子 Thread -> 结果汇总）是通用的。

SubAgentManager 核心设计

interface SubAgentConfig {
  id: string;
  parentId: string;              // 主 Agent 会话 ID
  task: string;                  // 自然语言任务描述
  systemPrompt: string;          // 注入的上下文（Engagement 子集）
  sandboxScope: string[];        // 此子 Agent 允许访问的网络范围
  timeout: number;               // 超时（秒）
  maxTokens: number;             // Token 预算
}

interface SubAgentResult {
  id: string;
  status: "completed" | "failed" | "timeout";
  findings: Finding[];           // 结构化发现
  rawOutput: string;             // 原始输出
  tokensUsed: number;
  duration: number;
}

class SubAgentManager {
  private agents: Map<string, SubAgentHandle> = new Map();
  private maxConcurrent: number = 4;     // 最大并发

  // 创建并启动子 Agent
  async spawn(config: SubAgentConfig): Promise<string> {
    // 等待并发槽位
    await this.waitForSlot();

    // 为子 Agent 创建独立的 Pi 会话
    const session = await createAgentSession({
      systemPrompt: config.systemPrompt,
      tools: this.filterToolsForSubAgent(config),
      sandbox: {
        level: 2,  // 子 Agent 默认 Layer 2 容器沙箱
        networkScope: config.sandboxScope,
      },
    });

    // 注入子 Agent 专用指令
    const handle = new SubAgentHandle(session, config);
    this.agents.set(config.id, handle);

    // 异步执行，不阻塞主 Agent
    handle.run().then(result => {
      this.onComplete(config.id, result);
    });

    return config.id;
  }

  // 等待所有子 Agent 完成
  async awaitAll(): Promise<SubAgentResult[]> {
    return Promise.all(
      [...this.agents.values()].map(h => h.promise)
    );
  }

  // 向主 Agent 汇报进度
  private onComplete(id: string, result: SubAgentResult) {
    // 写入 Engagement Memory（去重合并）
    engagementStore.mergeFindings(result.findings);
    // 通知主 Agent
    this.emit("sub_agent_complete", { id, result });
  }
}

6. 协调模式

子 Agent 之间的协调有三种基本模式，适用于不同场景：

模式一：Fan-out / Fan-in（扇出/扇入）

结构：主 Agent 将任务分成 N 份，N 个子 Agent 并行执行，全部完成后主 Agent 汇总。
适用：多目标扫描、多服务爆破 -- 子任务之间完全独立。
类比：MapReduce 的 Map 阶段。 

主 Agent: "扫描 192.168.1.0/24 的所有主机"
  |
  +-> 子 Agent A: nmap 192.168.1.1-64     (并行)
  +-> 子 Agent B: nmap 192.168.1.65-128   (并行)
  +-> 子 Agent C: nmap 192.168.1.129-192  (并行)
  +-> 子 Agent D: nmap 192.168.1.193-254  (并行)
  |
  汇总: 合并所有 Host/Service 发现 -> 写入 Engagement

模式二：Pipeline（流水线）

结构：阶段 A 的输出是阶段 B 的输入，每个阶段可以有多个子 Agent 并行。
适用：侦察 -> 漏洞扫描 -> 利用 这种有依赖关系的链条。
类比：Unix 管道，但每段可以 fan-out。 

阶段 1: 侦察 (4 个子 Agent 并行扫描)
  |
  v  发现 12 台主机
阶段 2: 漏洞扫描 (每台主机一个子 Agent)
  |
  v  发现 5 个潜在漏洞
阶段 3: 漏洞验证 (每个漏洞一个子 Agent)
  |
  v  确认 2 个可利用漏洞

模式三：Competitive（竞争式）

结构：多个子 Agent 尝试同一个问题的不同解法，第一个成功的终止其他。
适用：CTF 解题 -- 不确定哪种方向能解出来。
类比：Promise.race() 

目标: 获取 flag
  |
  +-> 子 Agent A: 尝试 SQL 注入     (竞争)
  +-> 子 Agent B: 尝试 XSS -> SSRF  (竞争)
  +-> 子 Agent C: 尝试目录遍历      (竞争)
  |
  Agent B 首先得到 flag -> 终止 A 和 C
面试知识点 -- 并发编排模式：Fan-out/Fan-in、Pipeline、Competitive 是三种经典的并发编排模式，在分布式系统中广泛使用。Fan-out/Fan-in 对应 MapReduce 和 Scatter-Gather 模式；Pipeline 对应流处理和 Actor chain；Competitive 对应 Hedged Request（Google 论文）和 Promise.race。AI Agent 的子 Agent 编排本质上就是分布式任务调度，只是"worker"不是线程或容器，而是独立的 LLM 会话。这三种模式也可以组合 -- 例如 Pipeline 的每个阶段内部用 Fan-out。

7. 子 Agent 与 Pi 集成

MilkSU 的子 Agent 需要在 Pi 框架内实现。Pi 的 createAgentSession() 已经支持创建独立的 Agent 会话，子 Agent 本质上就是由主 Agent 的工具调用触发的新会话。

实现方案：子 Agent 作为工具

// skills/orchestration/tools/spawn-agent.ts
export const spawnSubAgent = defineTool({
  name: "spawn_sub_agent",
  description: "创建子 Agent 执行独立任务。子 Agent 有自己的上下文和沙箱。",
  parameters: Type.Object({
    task: Type.String({ description: "子 Agent 的任务描述" }),
    scope: Type.Array(Type.String(), { description: "授权网络范围" }),
    tools: Type.Array(Type.String(), { description: "允许使用的工具列表" }),
  }),
  async execute({ task, scope, tools }) {
    const subAgentId = await subAgentManager.spawn({
      task,
      sandboxScope: scope,
      tools,
      parentId: currentSession.id,
      systemPrompt: buildSubAgentPrompt(task, scope),
      timeout: 600,
      maxTokens: 50000,
    });

    return {
      content: `子 Agent ${subAgentId} 已启动，任务: ${task}`,
      details: { subAgentId, status: "running" }
    };
  }
});

export const collectSubAgents = defineTool({
  name: "collect_sub_agents",
  description: "等待所有子 Agent 完成并收集结果",
  parameters: Type.Object({}),
  async execute() {
    const results = await subAgentManager.awaitAll();
    const summary = summarizeResults(results);

bridge.js 中的多会话管理

当前 bridge.js 管理单个 Pi 会话。子 Agent 需要扩展为多会话：

// bridge.js 扩展
class SessionPool {
  constructor(maxConcurrent = 4) {
    this.sessions = new Map();
    this.maxConcurrent = maxConcurrent;
  }

  async createSubSession(parentId, config) {
    const session = await createAgentSession({
      // 子 Agent 用相同的模型但独立的上下文
      model: config.model || parentSession.model,
      systemPrompt: config.systemPrompt,
      tools: config.tools,
    });

    // 子 Agent 的事件通过父会话的事件通道上报
    session.on("text_delta", (delta) => {
      parentSession.emit("sub_agent_delta", {
        subAgentId: config.id,
        delta,
      });
    });

    this.sessions.set(config.id, session);
    return session;
  }
}

8. 两种视觉交互范式

AI Agent 与浏览器/GUI 交互有两种截然不同的范式：

CDP（Chrome DevTools Protocol）

原理：通过 WebSocket 连接到 Chrome 的调试端口（默认 9222），发送 JSON-RPC 命令直接操控浏览器 DOM、网络、JavaScript 执行。

优势：精确、快速、可编程。可以直接读取 DOM 结构、执行 JS、拦截网络请求。

局限：只能操作 Chrome/Chromium 浏览器内的网页。无法操作原生应用、桌面 GUI、弹窗。

典型操作：page.click("#login-btn")、page.evaluate(() => document.title)

MilkSU 现状：browser-connect skill 已实现基本 CDP 连接

Computer Use（截图 + 坐标点击）

原理：对屏幕截图，用视觉语言模型（VLM）分析截图内容，输出要点击的坐标或要输入的文本，然后通过系统 API 模拟鼠标/键盘操作。

优势：通用性极强。可以操作任何可见的 GUI 元素 -- 浏览器、原生应用、远程桌面、甚至游戏界面。

局限：慢（每次操作需要截图 + VLM 推理，~1-3 秒），不够精确（坐标可能偏移），看不到隐藏元素。

典型操作：截图 -> VLM: "点击登录按钮" -> 返回 (423, 567) -> 模拟点击

典型用户：Anthropic Computer Use、Claude Code Chrome 扩展

两种范式的选择矩阵

场景 CDP Computer Use 推荐
Web 应用渗透测试 最佳 可用 CDP -- 可以直接操作 DOM、拦截 XHR、执行 JS
需要绕过 WAF/反爬 容易被检测 更像真人 Computer Use -- CDP 连接会被 navigator.webdriver 检测
已认证会话测试 最佳 可用 CDP -- 直接连接用户已登录的浏览器
原生应用测试 不可用 唯一选择 Computer Use -- CDP 不能操作非浏览器应用
Burp Suite 操控 不可用 可行 Computer Use -- 操作桌面 Java 应用
验证码交互 被阻止 视觉分析 Computer Use -- 但要注意合规性
MilkSU 策略：两者都要。CDP 作为默认的 Web 交互通道（快速、精确），Computer Use 作为后备和原生应用通道。Agent 根据目标类型自动选择：Web URL -> CDP，桌面应用 -> Computer Use，CDP 失败/被检测 -> 降级到 Computer Use。

9. Vision Loop 设计

Vision Loop 是 Computer Use 的核心架构：一个"截图 -> 分析 -> 操作 -> 再截图"的循环。

循环结构

while (!task.completed) {
  // 1. 截图
  const screenshot = await captureScreen();

  // 2. VLM 分析：当前状态 + 任务目标 -> 下一步操作
  const action = await vlm.analyze({
    image: screenshot,
    task: task.description,
    history: task.previousActions,  // 防止重复
  });

  // 3. 执行操作
  switch (action.type) {
    case "click":
      await mouse.click(action.x, action.y);
      break;
    case "type":
      await keyboard.type(action.text);
      break;
    case "scroll":
      await mouse.scroll(action.direction, action.amount);
      break;
    case "done":
      task.completed = true;
      task.result = action.result;
      break;
    case "failed":
      task.failed = true;
      task.error = action.reason;
      break;
  }

  // 4. 等待页面响应
  await wait(action.waitMs || 500);

  // 5. 安全检查：是否超出预期（误操作检测）
  if (task.actionCount++ > task.maxActions) {
    throw new Error("超过最大操作次数限制");
  }
}

VLM（视觉语言模型）选择

模型 提供者 特点 适用场景
Claude Sonnet (Computer Use) Anthropic 原生 Computer Use 支持，坐标精度高 通用 GUI 操作
GPT-4o OpenAI 强视觉理解，但无原生坐标输出 截图分析（非操控）
DeepSeek-VL2 DeepSeek 开源，可本地部署，但精度不及商用模型 隐私敏感场景
Qwen-VL-Max Alibaba 中文场景强，坐标理解逐步改善 中文 UI 操作
MilkSU 的 VLM 策略：默认用 DeepSeek（我们的主力 LLM 已有 VL 能力），但 Computer Use 场景允许用户配置专用的 VLM 端点。当用户配置了 Anthropic API Key 时，自动使用 Claude Sonnet 执行 Computer Use（精度最高）。这与模型选择器的多 provider 设计一致。

Tauri 集成方案

MilkSU 作为 Tauri App 有两个独特优势：

内嵌 WebView

Tauri v2 可以创建额外的 WebView 窗口。我们可以在 App 内打开目标网站，直接通过 Tauri 的 IPC 与 WebView 交互，无需 CDP 外部连接。这比 Codex CLI 更方便 -- CLI 无法内嵌浏览器。

系统级截图

Rust 后端可以通过 Core Graphics (macOS) / X11 (Linux) 截取屏幕截图，实现 Computer Use 的截图步骤。比 CDP 的 Page.captureScreenshot 范围更广，能捕获任何应用。

面试知识点 -- CDP（Chrome DevTools Protocol）：CDP 是 Chrome 浏览器暴露的远程调试协议，基于 WebSocket + JSON-RPC。它由若干"域"组成（Page、DOM、Network、Runtime、Debugger 等），每个域提供一组方法和事件。Puppeteer 和 Playwright 的底层都是 CDP。关键特性：双向通信（可以发命令也可以监听事件）、无状态方法（每个命令独立执行）、会话隔离（每个 tab 是独立的 debugging session）。安全领域的特殊用法：Network.setRequestInterception 拦截并修改 HTTP 请求（类似 Burp Proxy），Runtime.evaluate 在页面上下文执行 JS（类似 XSS payload 注入），DOM.getDocument 遍历完整 DOM 树（类似爬虫）。

12. 权限分类概念

自动模式（Auto Mode）要解决的问题：用户不想每次工具调用都手动确认，但也不想完全放弃控制。

行业方案

Claude Code: Auto Mode

使用分类器（小型 ML 模型或规则）判断每个工具调用的风险等级。低风险操作（读文件、运行测试）自动执行，高风险操作（删除文件、git push）请求确认。分类器的输入是工具名 + 参数，输出是 allow/deny。

Codex: execpolicy 规则引擎

使用 Starlark 规则语言定义命令权限。prefix_rule(pattern=["git","status"], decision="allow") 表示 git status 自动执行。prefix_rule(pattern=["rm","-rf"], decision="forbidden") 表示 rm -rf 永远禁止。支持三级决策：allow（自动执行）、prompt（请求确认）、forbidden（禁止）。

核心区别：Claude Code 用动态分类器（运行时判断），Codex 用静态规则（配置时定义）。Claude Code 更灵活（可以理解上下文），Codex 更可预测（规则是确定性的）。对安全工具场景来说，可预测性更重要 -- 安全测试者需要精确控制哪些操作自动执行，不能依赖分类器的"理解"。

13. Codex execpolicy 深度解析

Codex 的 execpolicy 是目前最成熟的开源权限引擎实现，值得深入学习。

规则语言（Starlark）

# Codex 默认规则示例（概念性重构，非逐行复制）

# Git 操作分级
prefix_rule(
    pattern = ["git", "status"],
    decision = "allow",       # git status 总是安全的
)

prefix_rule(
    pattern = ["git", "push"],
    decision = "prompt",      # git push 需要确认
    justification = "推送代码到远程仓库会影响其他人",
)

prefix_rule(
    pattern = ["git", "push", "--force"],
    decision = "forbidden",   # force push 永远禁止
    justification = "强制推送可能覆盖他人工作，使用 jj 或 --force-with-lease",
)

# 危险命令
prefix_rule(
    pattern = ["rm", "-rf"],
    decision = "forbidden",
    justification = "递归强制删除风险太高",
)

# 文件操作
prefix_rule(
    pattern = ["cat"],
    decision = "allow",       # 读文件总是安全的
)

匹配语义

  1. 前缀匹配：pattern = ["git", "status"] 匹配 git status、git status -s、git status --porcelain 等所有以 git status 开头的命令
  2. 备选项：pattern = ["git", ["commit", "add"]] 匹配 git commit 和 git add
  3. 优先级：更具体的规则优先。["git", "push", "--force"] 优先于 ["git", "push"]
  4. 默认行为：没有匹配规则时 -> prompt（请求确认）
  5. 内置测试：match 和 not_match 字段在规则加载时验证，相当于规则的单元测试

三级决策模型

决策 行为 用户体验 示例
allow 直接执行，不中断 用户看到执行结果，无需操作 git status, ls, cat, npm test
prompt 暂停，显示命令和理由，等待用户确认 用户看到弹窗，选择允许/拒绝 git push, npm install, docker run
forbidden 直接拒绝，Agent 收到错误信息 Agent 被告知此操作被禁止及原因 rm -rf, git push --force, sudo rm

14. MilkSU 安全工具风险模型

MilkSU 的自动模式需要在 Codex execpolicy 的基础上增加安全工具特有的维度：

四维风险评估

维度 低风险（allow） 中风险（prompt） 高风险（forbidden/需升级沙箱）
工具类型 被动信息收集：whois, dig, nslookup 主动扫描：nmap, masscan 漏洞利用：sqlmap, metasploit
目标授权 目标在 Engagement scope 内 目标部分在 scope 内 目标完全不在 scope 内
沙箱等级 工具在声明的沙箱等级内运行 工具请求降低沙箱等级 工具尝试逃逸沙箱
破坏性 只读操作（扫描、查询） 可逆写入（发送探测包） 不可逆操作（数据库写入、文件删除）

15. 沙箱感知的自动审批

MilkSU 的自动模式与沙箱系统深度联动 -- 沙箱等级影响审批决策，审批决策影响沙箱配置。

决策流程

工具调用进入 policy-engine
  |
  v
[1] execpolicy 规则匹配
    |
    +-- forbidden -> 立即拒绝，返回原因
    |
    +-- allow -> 进入沙箱检查
    |
    +-- prompt -> 进入确认流程
    |
    +-- no match -> 默认 prompt
    |
    v
[2] 沙箱等级检查
    |
    +-- 工具声明 Layer N
    +-- 全局策略要求 Layer M
    +-- 实际等级 = max(N, M)
    |
    v
[3] scope 校验（如需网络）
    |
    +-- 目标在 scope 内 -> 继续
    +-- 目标不在 scope 内 -> 拒绝（无论 allow/prompt）
    |
    v
[4] 执行（在对应沙箱等级中）
    |
    v
[5] 结果 -> 三通道分发（Agent / Memory / Panel）

Human-in-the-Loop 确认界面

自动审批的安全保障

硬性约束（不可覆盖）：
  • 没有 active Engagement 时，所有网络工具调用被拒绝
  • 目标不在 scope 内时，即使规则是 allow，也被拒绝
  • 子 Agent 的权限不能超过主 Agent 的权限
  • forbidden 规则不可通过"总是允许"覆盖
  • 沙箱等级只能提升不能降低
面试知识点 -- 权限分类器 vs 规则引擎：这是两种截然不同的权限控制策略。分类器（Claude Code）的优势是灵活 -- 可以理解上下文（"这个 rm 是在删临时文件，安全"），但劣势是不确定性 -- 分类器可能误判。规则引擎（Codex execpolicy）的优势是确定性 -- 规则的行为完全可预测，但劣势是需要人工编写规则，难以覆盖所有边缘情况。

MilkSU 选择规则引擎而非分类器的原因：安全工具场景下，误放行（False Positive Allow）的后果远大于误拒绝（False Positive Deny）。一个被误放行的 sqlmap --os-shell 可能导致目标系统被完全控制；而一个被误拒绝的 nmap -sV 只是让用户多点一次确认。在这种不对称风险下，规则引擎的确定性比分类器的灵活性更重要。

17. 实现优先级

基于依赖关系和价值排序：

Phase 0: 前置条件（1 周）

完成 end-to-end agent loop（bridge.js + DeepSeek API Key）。所有后续系统都依赖一个能运行的 Agent。

Phase 1: 自动模式（2 周）

为什么先做：不需要沙箱和记忆就能工作（规则引擎 + 确认对话框），且立即改善用户体验（减少手动确认）。
内容：execpolicy 规则解析器、三级决策逻辑、前端确认对话框、"本次/总是"允许机制
Codex 参考：codex-rs/execpolicy 的规则语法和匹配逻辑

Phase 2: 浏览器 CDP 增强（2 周）

为什么第二：browser-connect skill 已有基础 CDP 连接。增强为完整的 Web 测试工具集（DOM 遍历、请求拦截、JS 执行）价值高。
内容：browser_interact / browser_intercept / browser_analyze 工具、BrowserRouter 协议选择
不做 Computer Use：CDP 已覆盖 80% 的 Web 测试场景，Computer Use 留到后面

Phase 3: 子 Agent（3 周）

为什么第三：子 Agent 需要自动模式（子 Agent 的工具调用也要过 policy）和记忆系统（共享状态）。
内容：SubAgentManager、bridge.js 多会话池、spawn/collect 工具、前端进度展示
先做简单版：Fan-out/Fan-in 模式，最多 4 个并发，后续再加 Pipeline 和 Competitive

Phase 4: Computer Use + Vision Loop（远期）

为什么最后：需要 VLM 集成，依赖模型能力进步。当前 DeepSeek-VL 的坐标精度不够，等模型成熟。

18. 面试知识点

Codex 开源复用

开源代码的三层复用策略

代码级（直接引用/fork 源码）、架构级（学习设计模式和分层方式）、概念级（借鉴解决问题的思路）。判断复用层次的关键：问题域是否相同。Codex 的沙箱（Seatbelt SBPL）和规则引擎（execpolicy Starlark）可以代码级复用；记忆系统可以架构级复用；子 Agent 编排只能概念级复用。

CLI vs App 的架构边界

成熟的系统都会将"引擎层"和"展示层"解耦。Codex 的 codex-rs/core（引擎）和 codex-rs/tui（展示）就是两个独立的 crate。这意味着 CLI 的引擎可以驱动 GUI App -- 前端从 Ratatui 换成 React，后端逻辑（agent loop, sandboxing, policy）不变。MilkSU 的"bridge.js 子进程"架构天然支持这种解耦 -- Rust 后端不关心 Agent 逻辑，只管进程生命周期和事件转发。

子 Agent

并发编排三模式

Fan-out/Fan-in（MapReduce/Scatter-Gather）、Pipeline（流处理/Actor chain）、Competitive（Hedged Request/Promise.race）。AI Agent 子任务编排本质上是分布式任务调度 -- worker 不是线程而是独立的 LLM 会话。关键挑战：上下文隔离（每个子 Agent 独立的 token 窗口）、状态同步（共享 Engagement Memory）、资源控制（并发数限制、token 预算）。

浏览器控制

CDP vs Computer Use 选择矩阵

CDP（Chrome DevTools Protocol）是结构化的浏览器控制 -- 精确、快速、可编程，但只能操作 Web 内容。Computer Use 是视觉驱动的通用 GUI 控制 -- 通用但慢、不够精确。选择策略：Web 目标用 CDP（80% 场景），桌面应用用 Computer Use（20% 场景），CDP 被反爬检测时降级到 Computer Use。两者不是替代关系而是互补关系。

自动模式

规则引擎 vs 分类器：不对称风险下的选择

当误放行（false allow）的后果远大于误拒绝（false deny）时，选择确定性的规则引擎优于概率性的分类器。安全工具场景就是典型的不对称风险 -- 一个被误放行的漏洞利用命令可能造成不可逆损害，而一个被误拒绝的扫描命令只需要用户多点一次确认。这个原则在金融、医疗等高风险领域同样适用。

Starlark 作为配置语言

Codex 选择 Starlark（Python 的确定性子集，由 Google 为 Bazel 开发）作为规则语言，而不是 YAML/JSON/TOML。原因：Starlark 支持函数调用语法（prefix_rule(...)），比声明式格式更适合表达带逻辑的规则；同时它是"纯确定性"的（没有 import、没有 I/O、没有随机数），保证配置的可重现性。这是"内嵌 DSL"设计模式 -- 用一个受限的通用语言代替自制的配置格式。
