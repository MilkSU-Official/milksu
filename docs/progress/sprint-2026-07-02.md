## 发现的架构问题

### 严重

1. **Engagement 与 TaskState 数据重复** -- `Engagement` 拥有 `EngagementHost` (ip, services, vulnerabilities)。`PentestState` 拥有 `ports[]` 和 `vulnerabilities[]`。`ReconState` 拥有 `hosts[]` 和 `ports[]`。相同数据, 不同结构, 之间无同步。panel_update 写入 TaskState; engagement CRUD 写入 Engagement。

2. **单 bridge 进程, 单对话** -- `bridge.js` 使用模块级 `currentPromptId` 和单个 `session`。所有事件携带最后设置的 prompt ID。Rust 端持有 `Mutex<Option<BridgeProcess>>` -- 整个应用只有一个 bridge。无对话隔离。

### 警告

3. **App.tsx 上帝组件** -- 394 行, 11 个 useState, 7 个 useCallback, 3 个 useEffect。包揽对话 CRUD、消息路由、面板合并、engagement 状态、设置、任务类型切换、布局切换。每次冲刺都在增长这个文件。

4. **浏览器工具共享可变模块状态** -- `intercept.ts` 和 `network.ts` 拥有模块级数组和标志。如果两个对话使用浏览器工具, 它们会共享日志和路由处理器。

### 次要

5. **Bridge 崩溃 = 静默死亡** -- 如果 bridge.js 崩溃, stdout 读取线程静默退出。`Mutex<Option<BridgeProcess>>` 仍然持有 `Some(...)` 但 stdin 已死。无重连, 无 UI 通知。

6. **camelCase/snake_case 边界脆弱** -- 前端 camelCase, Rust snake_case。在 `fromStored()`/`toStored()` 和 `commandArg()` 中手动映射。每个新字段需要在 3 处维护映射。
